# Архитектура Proxima Traffic

Этот документ — рабочий контракт проекта. Если новое решение противоречит ему, сначала
обновляется и согласуется архитектура, и только потом меняется код.

## 1. Что строим

Proxima Traffic — персональный локальный комплекс с управлением через отдельного
Telegram-бота. Бот является единственной пользовательской админкой. Веб-сайт и
браузерная панель в продукт не входят.

Основные сценарии исполнения:

1. **Рассылка:** оператор выбирает собственные аккаунты, чат/базу и текст, затем запускает
   одноразовый проход с окном распределения либо умную непрерывную публикацию на заданный срок.
2. **Диалог:** первый собственный аккаунт отправляет сообщение, а второй после заданной
   задержки отвечает через `reply_to_message_id`.
3. Каждый шаг, Telegram message ID, ошибка, повтор и конечный результат сохраняются в БД
   и отображаются ботом.
4. Перед live-отправкой применяются таймер чата, Telegram slow mode, pace/FloodWait аккаунта
   и обязательный исправный прокси-маршрут.

## 2. Главные архитектурные решения

- Интерфейс: aiogram 3, inline-кнопки и редактирование одного меню.
- Состояния ввода: FSM с явной кнопкой отмены и возврата.
- Хранилище: SQLite для одного локального процесса; PostgreSQL допускается позднее.
- ORM и миграции: SQLAlchemy 2 + Alembic.
- Исполнение: постоянная очередь с lease, идемпотентностью, повторами и отменой.
- Шлюзы: безопасный `dry-run` и live Telethon через импортированные `tdata`/`.session`.
- Админ-доступ: строгий allowlist Telegram user ID, а не знание команды `/admin`.
- Секреты: токены и авторизационные данные не хранятся открыто в репозитории или логах.

## 3. Компоненты

### 3.1 Control Bot

Отвечает только за взаимодействие с оператором:

- `/start`, `/admin`, `/cancel`;
- главный экран со статистикой;
- аккаунты и их состояния;
- разрешённые цели и базы чатов;
- шаблоны сообщений;
- кампании и параметры запуска;
- очередь, остановка и повтор задач;
- журнал результатов и системный аудит;
- уведомления о завершениях и критических ошибках.
- полный операторский раздел прокси: импорт, группы, фильтры, проверки, карантин и назначения.

Массовые отправки бот не выполняет внутри обработчика update: он создаёт durable-задачи в БД.
Операторские действия вроде проверки одной сессии, профиля, папки или ротации выполняются с
явным timeout и показывают итог в той же карточке.

### 3.2 Application Services

Содержит бизнес-правила без зависимости от aiogram:

- подтверждение владения аккаунтами;
- разрешение/отзыв целей;
- валидация сценария;
- создание идемпотентного запуска;
- переходы состояний запуска;
- формирование аудита.

### 3.3 Durable Queue

Очередь хранится в основной БД. Состояния запуска:

`queued -> running -> queued(reply delay) -> running -> succeeded`

Альтернативные терминальные состояния: `failed`, `cancelled`.

Инварианты:

- один `request_key` создаёт не более одного запуска;
- умный запуск создаёт только одну следующую задачу на логический поток; в независимом режиме
  поток равен паре `account_id + target_id`, после успеха остаётся у того же аккаунта и не влияет
  на параллельные пары;
- интервал пары обучается по числу сообщений и прошедшему времени, сглаживается между циклами,
  но Telegram/ручной таймер, pace, FloodWait и дедлайн остаются жёсткими границами;
- настройки запуска, пул отправителей и тексты сохраняются снимком и не меняются при последующем
  редактировании сценария;
- при фатальной ошибке отправителя задача может перейти только к доступному аккаунту из снимка
  выбранного пула; каждая замена сохраняется в action log и audit;
- индивидуальный таймер хранится для пары `target_id + account_id` и переживает рестарт;
- воркер получает временный lease;
- протухший lease восстанавливается;
- успешный первый шаг не выполняется повторно при ошибке ответа;
- задержка ответа хранится как `scheduled_for`, а не как долгий `sleep`;
- отменённый запуск больше не получает новые шаги;
- после исчерпания попыток задача становится `failed`.
- каждая аренда получает новый `lease_token`; запись результата разрешена только владельцу этого токена;
- heartbeat продлевает только текущую аренду и не может оживить устаревший token;
- recovery использует compare-and-set по token и повторно проверяет срок lease в момент UPDATE;
- timeout и неизвестная ошибка считаются результатом с неопределённым внешним эффектом и не повторяются автоматически;
- повтор разрешён только для явно классифицированной временной gateway-ошибки;
- каждый gateway-вызов получает стабильный `idempotency_key` вида `request_key:step`;
- сообщения ошибок очищаются от паролей в URL перед записью в БД и аудит.

### 3.4 Execution Worker

Воркер берёт один готовый шаг, вызывает абстракцию `MessageGateway`, сохраняет результат
и освобождает lease. В локальной конфигурации работает один воркер. Для PostgreSQL позже
добавляется безопасный многопроцессный claim через `FOR UPDATE SKIP LOCKED`.

Текущая SQLite-реализация использует WAL, `busy_timeout`, атомарный условный UPDATE и локальную
сериализацию claim. Параллельность worker настраивается, но по умолчанию равна одному потоку.

### 3.5 Message Gateway

Контракт отправки:

- вход: аккаунт, цель, текст и необязательный `reply_to_message_id`;
- выход: подтверждённый `message_id`;
- классифицированные ошибки: авторизация, ограничение, сеть, недоступная цель.

Реализации: `DryRunGateway` и `TelethonGateway`. Live-шлюз использует зашифрованный
`StringSession`, подключается только через назначенный HEALTHY-прокси, проверяет членство,
права на конкретные типы контента и slow mode, а после отправки подтверждает наличие сообщения.
Один аккаунт обслуживается одним кэшированным клиентом и одним lock: проверки, профиль, аватары,
папки и отправка не открывают конкурирующие соединения с тем же `auth_key`. Альбом проходит
`messages.uploadMedia` до `messages.sendMultiMedia`, а серверные ожидания Telegram не сокращаются.

## 4. Модель данных

### Уже заложено

- `accounts` — реестр аккаунтов и подтверждение владения;
- `targets` — отдельные чаты с ручным допуском;
- `target_account_states` — slow mode, следующее разрешённое время, последняя доставка,
  членство и право писать конкретного аккаунта в конкретном чате;
- `target_lists` и `target_list_items` — именованные базы целей; флаг `enabled` принадлежит
  конкретному членству, поэтому общий чат включается независимо в каждой базе;
- `message_templates` — библиотека парных шаблонов;
- `campaigns` — режим, отправители, цель, тексты/HTML, локальное медиа, окно одноразового
  прохода, срок/интервал/глубина умной рассылки и настройка автозамены;
- `campaign_runs` — durable-очередь, дедлайн и снимки параметров, текущий отправитель, шаг длинной
  диалоговой цепочки, lease, попытки, статус и обратимый архив запуска;
- `action_logs` — результат каждой отправки;
- `audit_events` — административные и системные изменения.
- `proxy_groups` — именованные пулы прокси;
- `proxy_endpoints` — адреса, зашифрованные пароли, состояние и метрики проверок;
- `proxy_assignments` — эксклюзивные назначения исправных прокси на именованные слоты.

Запуск по базе разворачивается в отдельные `campaign_runs`, каждый из которых сохраняет
свой `target_id`. Это фиксирует состав выполняемых задач даже при дальнейшем изменении базы.

## 5. Экраны Telegram-бота

Главное меню:

- `➕ СОЗДАТЬ ЗАКАЗ` — единая изменяемая карточка рассылки или диалога;
- `📡 Запуски и отчёты`: операторская сводка состояния, покрытия, проблем, потоков и публикаций;
- обратимый архив завершённых запусков;
- `🗂 Сценарии`;
- `🎯 Аудитории` — отдельно базы и ручные чаты;
- `👥 Аккаунты`, `📝 Тексты`, `🌐 Прокси`;
- `⚙️ Система`, `↻ Обновить`.

Каждый экран:

- редактирует текущее сообщение вместо создания ленты сообщений;
- имеет кнопку `⬅️ Назад`;
- использует пагинацию с предыдущей/следующей страницей, прыжком ±10, началом/концом и поиском;
- отвечает на каждый callback query;
- показывает понятный итог после операции;
- при FSM-вводе предоставляет явную кнопку отмены и возврата;
- использует единый заголовок, краткую сводку и явные названия действий вместо кнопок-иконок;
- удаляет обработанные сообщения оператора внутри FSM, сохраняя чат как одну рабочую панель;
- требует отдельного подтверждения для удаления и постановки кампании в очередь;
- не показывает пагинацию, когда список помещается на одной странице.

## 6. Безопасность и границы

- Админ-бот отвечает только ID из `PROXIMA_BOT_ADMIN_IDS`.
- Проект принимает только собственные `tdata`/`.session`; `tdata` используется один раз для
  подтверждения отдельной серверной сессии с собственным API ID, исходный ключ Desktop не
  сохраняется. Все серверные сессии шифруются отдельным неизменяемым ключом; OTP бот не
  запрашивает, а пароль 2FA можно передать только временным секретом окружения.
- Цель не исполняется без ручного допуска.
- Аккаунт не исполняется без подтверждения владения.
- LIVE-запуск не создаётся без свежей preflight-карты членства и права писать для всей
  аудитории; проверка не вступает в чаты и ничего не отправляет.
- Медиа разрешено читать только из выделенного локального каталога с проверкой размера.
- `dry-run`, отдельный `LIVE_EXECUTION_ARMED` и выключаемый worker образуют тройной
  предохранитель от случайной отправки.
- Обход капч, ограничений Telegram и маскировка автоматизации не входят в проект.
- Пароли прокси шифруются отдельным ключом, не возвращаются из API и не показываются ботом.
- Ошибки сетевой проверки очищаются от URL и учётных данных перед записью в БД и аудит.
- Аккаунтный transport получает сеть только через обязательный слот `account:<id>`.
- Отсутствующий, выключенный или не прошедший проверку прокси запрещает запуск; direct fallback нет.
- Для SOCKS DNS разрешается удалённо; production дополняется egress firewall против IP/DNS/IPv6 leak.
- Bot API не раскрывает `t.me/addlist/...`; папка требует user-only MTProto preview и явного выбора.

## 7. Процессы запуска

- `proxima-bot` — основной процесс: control bot + локальный worker.
- `proxima-api` — необязательный диагностический API для разработки и тестов.
- `alembic upgrade head` — обновление схемы перед production-запуском.

## 8. Порядок реализации

1. Стабилизировать текущую очередь, миграцию и тесты.
2. Реализовать закрытый aiogram-бот и главное inline-меню.
3. Добавить FSM аккаунтов, целей и кампаний.
4. Добавить управление запусками, отмену, детали и аудит.
5. Вынести шаблоны и базы целей в отдельные таблицы.
6. Добавить уведомления, резервное копирование и эксплуатационные команды.
7. Провести полный сквозной dry-run тест очереди и интерфейса.
