## CR-CURRENT-008 — P1: неожиданное падение шага реакции оставляло задачу в lease и допускало неоднозначный повтор

- **Где:** `src/proxima_traffic/reactions.py` и `src/proxima_traffic/participant_reactions.py`, `process_next()`.
- **Доказательство:** обе функции ловили `Exception` вокруг `_process()` и только логировали её. Задача оставалась `RUNNING` до истечения lease; затем recovery возвращал её в очередь. Для неизвестной ошибки это небезопасно: вызов Telegram мог уже поставить реакцию, а повтор после recovery создаёт неоднозначный внешний эффект. Это противоречит правилу очереди, по которому неизвестная ошибка должна стать терминальным результатом.
- **Эффект:** обычная или participant-реакция могла висеть до lease timeout, после чего повторяться без классификации причины; UI долго не показывал финальный результат.
- **Исправлено:** оба worker-а передают исключение в durable `_handle_error()`. Неклассифицированная ошибка становится терминальной (`reaction_failed` / `participant_reaction_failed`) и немедленно освобождает lease, поэтому не создаёт автоматический повтор при recovery. Добавлены тесты, которые принудительно аварийно завершают `_process()` и проверяют `FAILED`, код ошибки и очищенный lease для обоих видов реакций.

## CR-CURRENT-010 — P1: первое сканирование participant reactions может поставить реакции на старую историю чата

- **Где:** `src/proxima_traffic/live_gateway.py:679–685` и `src/proxima_traffic/participant_reactions.py:416–448`.
- **Доказательство:** при новом правиле `last_seen_message_id` равен 0, а `primed=False`. `scan_participant_messages()` вызывает Telethon `iter_messages(..., min_id=0, reverse=True, limit=N)`. В таком направлении Telegram отдаёт наиболее раннюю доступную страницу сообщений, а не последние N. `_persist_scan()` на первом вызове ставит cursor на максимальный id этой старой страницы и возвращает. На следующем сканировании cursor уже primed, функция берёт следующую старую страницу, создаёт для неё reaction tasks, затем продолжает так до текущих сообщений. Комментарий в коде и контракт функции заявляют обратное: «old chat history is never engaged».
- **Эффект:** после подключения правила к давно существующему чату сервис способен массово отреагировать на исторические сообщения вместо реакции только на новые сообщения после включения правила. Это нарушает ожидаемое поведение и существенно повышает риск нежелательной активности аккаунтов.
- **Рекомендация:** для непроинициализированного cursor получать именно самый новый message id (один newest-first запрос без `reverse=True`), сохранять его как checkpoint и не создавать задач. Лишь для уже primed cursor читать вперёд `min_id=checkpoint, reverse=True`. Добавить тест с историей значительно больше `participant_reactions_scan_limit`: первый scan не создаёт задач и сохраняет id последнего сообщения; второй создаёт задачи только для сообщений, появившихся после этого id.
- **Исправлено:** scanner передаёт `bootstrap=True` для непроинициализированного cursor. Live gateway в таком режиме запрашивает только одно newest-first сообщение, сохраняемое существующей веткой priming без создания reaction task. После priming gateway снова читает вперёд от cursor с `min_id` и `reverse=True`. Добавлены проверки обоих режимов gateway и флага bootstrap у сервиса.

- **Где:** `src/proxima_traffic/live_gateway.py:396–405` и `src/proxima_traffic/channel_comments.py:437–449, 514–564`.
- **Доказательство:** у нового `ChannelCommentRule.last_seen_post_id` равен 0. Gateway запрашивает `iter_messages(channel, min_id=0, reverse=True, limit=N)`. Локально установленная версия Telethon 1.44.0 документирует `reverse=True` как выдачу «from oldest to newest», поэтому первая страница — самые ранние N постов. `_store_scan()` честно пропускает их по `armed_at`, но сохраняет только id этой ранней страницы. Каждый следующий интервал он проходит ещё N старых постов. Новый пост может быть замечен лишь после обхода всей истории: при 50 000 постов, лимите 30 и интервале 60 секунд это порядка 28 часов.
- **Эффект:** comments-rule выглядит включённым и без ошибок, но не комментирует новые посты у давно существующего канала. Более того, после догоняющего прохода старые посты, опубликованные уже после `armed_at`, могут быть обработаны значительно позже предусмотренного initial delay.
- **Рекомендация:** на первом scan получать только последний пост newest-first и записывать его id как стартовый checkpoint (без создания comment run); дальнейшие scan выполнять вперёд от checkpoint с `reverse=True`. Добавить интеграционный fake-Telethon тест с длинной историей, который проверяет: включение правила не перебирает архив, а следующий новый пост становится `QUEUED` сразу.
- **Исправлено:** новый comments-rule передаёт `bootstrap=True`, и live gateway читает лишь текущий newest-first пост вместо первой страницы архива. Обычная обработка `armed_at` остаётся прежней: пост после включения правила может быть поставлен в очередь, архивный — пропускается; последующие запросы снова идут вперёд от cursor. Добавлен тест точного bootstrap-вызова gateway.

## CR-CURRENT-012 — P1: зависшая отправка комментария не ограничена timeout и маскируется heartbeat-ом

- **Где:** `src/proxima_traffic/channel_comments.py:451–467, 656–746`; настройка `worker_step_timeout_seconds` используется в `services.py`, `reactions.py` и `participant_reactions.py`, но не здесь.
- **Доказательство:** `ChannelCommentService.process_next()` вызывает `_process_claimed()` без `asyncio.timeout`. Внутри тот ждёт gateway-вызовы `send_channel_comment()`/`edit_channel_comment()` через account lock без локального deadline. Параллельный `_heartbeat()` каждые `worker_heartbeat_seconds` продлевает `lease_until`, пока операция висит. Поэтому recovery не вернёт работу в очередь, а `WorkerSupervisor` не получит результат итерации и продолжит отображать ранее успешное состояние `running`.
- **Эффект:** один зависший MTProto/RPC-вызов блокирует единственный цикл комментариев на неограниченное время, удерживает конкретный comment-run навсегда и скрывает проблему от `/ready` и dashboard. Новые комментарии не обрабатываются.
- **Рекомендация:** обернуть обработку одного claimed run в тот же `asyncio.timeout(settings.worker_step_timeout_seconds)`, как в reaction workers; на timeout передавать контролируемый временный error в `_handle_delivery_error()` и освобождать lease с retry. Добавить тест с gateway, который ждёт `Event` бесконечно: задача должна выйти по timeout, получить retry-status и освобождённый lease.
- **Исправлено:** `process_next()` ограничивает один comment-run настройкой `worker_step_timeout_seconds`. При timeout он сохраняет `comment_timeout`, освобождает lease и откладывает повтор через существующую durable retry-ветку. Тест с намеренно не завершающимся gateway подтверждает, что задача остаётся `QUEUED` без lease.

## CR-CURRENT-013 — P2: participant reactions может реагировать на сообщения другого подключённого сервисного аккаунта

- **Где:** `src/proxima_traffic/participant_reactions.py:339–360, 428–445`.
- **Доказательство:** комментарий модуля обещает «never reacts to a known service account's own message». Однако `own_sender_ids` строится только из `accounts`, выбранных в текущем rule как реакторы. В `_persist_scan()` единственная защита — `message.sender_id in own_sender_ids`. Сервис не запрашивает и не исключает Telegram user id остальных `Account` в БД. Сценарий: rule использует аккаунт A как реактор, а рассылку в этот чат ранее отправил ваш аккаунт B; B отсутствует в `rule.account_ids`, поэтому сообщение B считается участником и A может поставить на него реакцию.
- **Эффект:** сервис нарушает семантику «реакции на сообщения участников» и может создавать искусственные взаимодействия между вашими собственными аккаунтами. Это также создаёт лишнюю активность и искажает статистику правила.
- **Рекомендация:** перед scan получать set всех подтверждённых собственных `Account.telegram_user_id` (или хранить/обновлять такой set централизованно) и передавать его в `_persist_scan()`. Тест должен включать три аккаунта: A выбран как reactor, B — не выбран, C — внешний; задача создаётся только для сообщения C.
- **Исправлено:** scanner получает Telegram ID всех собственных аккаунтов из БД, независимо
  от состава текущего rule, и исключает их до создания задач. Регресс включает выбранные и
  невыбранный собственный аккаунт и создаёт задачу только для внешнего участника.
