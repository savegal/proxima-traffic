## Методика и границы

Для каждого блока проверяются:

1. пользовательский путь в control-боте и доступный API-контракт;
2. серверная валидация, права и устойчивость состояния в БД;
3. исполнение в очереди, повторы, отмена, рестарт и параллельность;
4. реальная Telegram-интеграция по коду и изолированные тесты;
5. качество: наблюдаемость, понятные статусы, тестовое покрытие и граничные случаи.

Фактическая отправка в production Telegram в рамках аудита не запускается: это требует
отдельно выделенных тестовых аккаунтов и явно заданной тестовой аудитории. Проверка кода,
миграций, dry-run и тестов выполняется локально.

### Готовность именно текущего личного экземпляра

Текущий экземпляр после исправлений остаётся **намеренно не включённым для реальных
отправок**, даже если логика кампании настроена правильно:

- `dry_run=True` и `live_execution_armed=False` — реальное исполнение не вооружено;
- `worker_enabled=False` и `api_worker_enabled=False` — ни bot-процесс, ни API-процесс не
  поднимают workers рассылок, комментариев и реакций;
- настроенная БД `proxima-clean.db` обновлена с `0045_notification_delivery_leases` через
  `0046` до `0047_critical_execution_safety`; integrity/FK/schema проверки пройдены,
  `doctor` возвращает healthy;
- в БД есть 4 активных аккаунта, но нет кампаний, запусков, comment rules/runs,
  reaction tasks и participant-reaction rules/tasks. На личных данных поэтому нельзя было
  проверить завершённый пользовательский сценарий без создания новых сущностей и
  реальной внешней активности.

Это безопасное состояние окружения, а не поломка: миграция уже применена, но до отдельного
безопасного preflight и opt-in live smoke нельзя включать worker и вооружать production.

#### RA1-ENV-01 — BLOCKER: текущий экземпляр не исполняет очереди

- **Текущий статус:** миграционная часть исправлена — backup создан, БД обновлена до
  `0047`, doctor healthy. `dry_run`/workers/live остаются выключенными намеренно до opt-in
  проверки и больше не считаются дефектом кода.

- **Доказательство:** фактические настройки и revision БД приведены выше. `bot_main`
  запускает campaign/comments/reactions/participant/delivery workers только при
  `worker_enabled`; API делает это только при `api_worker_enabled`.
- **Эффект:** правила и запуски могут быть сохранены, но фоновой отправки в текущей
  конфигурации не будет. `dry_run` и отсутствие armed-флага дополнительно исключают live.
- **Что осталось перед live:** выбрать ровно один процесс-владелец workers, прогнать
  preflight и Test DC smoke; только затем отдельно включать live на тестовой аудитории.

#### RA1-01 — P1: поздний retry не восстанавливает уже принятую отправку

- **Статус:** **исправлено 06.08.2026** миграцией `0047` и durable
  `TelegramDeliveryReceipt`; первая попытка и известный external message ID переживают
  рестарт/долгий retry. Добавлен десятиминутный regression test.

- **Где:** `src/proxima_traffic/live_gateway.py:1761–1779, 1815–1830,
  1869–1905, 1957–1984, 2012–2060`.
- **Доказательство:** `sent_after=utc_now()` создаётся заново перед каждой попыткой.
  `_recover_duplicate_delivery()` и contact-аналог прекращают поиск, если найденное
  исходящее сообщение старше `sent_after - 2 минуты`. Через три минуты корректное
  outgoing-сообщение с тем же текстом и reply воспроизводимо возвращает `None`.
- **Эффект:** Telegram уже доставил сообщение один раз и по стабильному `random_id` не
  создаст дубль, но сервис после повторов может отметить run как failed, не получить
  message ID, не обновить pacing/отчёт и не поставить связанные реакции.
- **Что сделать:** хранить timestamp первой фактической send-attempt в durable задаче либо
  восстанавливать по стабильному random-id/API-результату без привязки к времени текущего
  retry; добавить тест с интервалом больше двух минут для текста, HTML, media, album,
  contact и comment reply.

#### RA1-02 — P1: общий lock не делает проверку pacing атомарной

- **Статус:** **исправлено 06.08.2026**. В Account добавлена атомарная send reservation с
  token/expiry/heartbeat; campaigns, comments и оба reaction worker-а повторно проверяют
  pacing после cross-process claim и завершают счётчики под тем же владением.

- **Где:** `src/proxima_traffic/reactions.py:250–270`,
  `participant_reactions.py:596–613`, `channel_comments.py:713–769` и
  `services.py:228–255`.
- **Доказательство:** worker читает `account_resume_at(account)` до входа в
  `run_account_operation()`. Общий `asyncio.Lock` сериализует только closure с Telegram
  вызовом и последующим `record_external_account_send()`, но после ожидания lock второй
  worker не перечитывает Account и не повторяет проверку. Campaign-reaction и
  participant-reaction loops работают параллельно и могут оба увидеть аккаунт свободным.
  Межпроцессный gateway lease заканчивается до отдельного commit счётчиков, что оставляет
  аналогичное окно между процессами.
- **Эффект:** две реакции/комментарий могут уйти почти подряд вопреки диапазону 45–120 с;
  дневной лимит и micro-break проверяются по устаревшему состоянию.
- **Что сделать:** внутри единой account-operation транзакции после получения локального и
  БД-lease заново загрузить Account, атомарно зарезервировать pacing slot/counters и только
  затем выполнять Telegram call. Добавить конкурентный тест минимум для двух разных
  worker-типов и второй процесс/runner.

#### RA1-03 — P2: реакция возможна на другой собственный аккаунт

- **Где:** `src/proxima_traffic/participant_reactions.py:353–361, 405–445`.
- **Доказательство:** `own_sender_ids` строится только из `accounts`, выбранных в текущем
  rule. Сообщение любого другого подтверждённого Account из той же БД не исключается.
- **Эффект:** аккаунт A может ставить реакцию на сообщение вашего аккаунта B, если B не
  включён в reactor pool; статистика «реакций на участников» искажается.
- **Что сделать:** исключать Telegram user ID всех подтверждённых собственных аккаунтов;
  тест A/B/external должен создавать задачу только для external.

#### RA1-04 — P2: смена автора обрывает начатый диалог комментариев

- **Где:** `src/proxima_traffic/channel_comments.py:295–383`.
- **Доказательство:** для `MESSAGE_EDIT` блокируется `RUNNING` и `QUEUED & sent_steps>0`;
  для `DIALOGUE` проверяется только `RUNNING`. После каждого шага `_record_delivery()`
  возвращает цепочку в `QUEUED` на время delay, уже с `sent_steps>0`. Замена автора затем
  массово переводит все `QUEUED` runs в `CANCELLED`.
- **Эффект:** первый комментарий остаётся в Telegram, продолжение никогда не отправится;
  интерфейс/README обещает отмену неначатых старых задач, но отменяется уже начатая.
- **Что сделать:** для dialogue применить ту же проверку `QUEUED & sent_steps>0` либо
  сохранить полный immutable snapshot цепочки и дать ей завершиться; добавить тест замены
  во время межшаговой задержки.

#### RA1-05 — P2: реакции отдельного запуска нельзя остановить после публикаций

- **Где:** `src/proxima_traffic/bot/repository.py:163–205`,
  `bot/keyboards.py:2446–2494`, `bot/handlers.py:9497`,
  `services.py:3867–3925`.
- **Доказательство:** `LaunchView.active = queued + running` и не включает
  `reaction_queued + reaction_running`. Кнопка cancel и handler доступны только при
  `launch.active`, хотя `cancel_launch()` умеет отменять связанные ReactionTask.
- **Эффект:** как только основные сообщения успешно завершены, а реакции только начались
  или ждут задержку/pacing, оператор может лишь выключить реакции кампании целиком или
  сделать глобальный stop; остановить один конкретный запуск из его карточки нельзя.
- **Что сделать:** добавить `has_pending_work` или включить реакции в операционную
  активность; показывать отдельную кнопку «остановить реакции запуска» и блокировать архив,
  пока они не терминальны (либо явно архивировать весь composite launch).

#### RA1-06 — P2: participant reactions не имеют per-chat failover

- **Где:** `src/proxima_traffic/participant_reactions.py:335–398, 930–936`.
- **Доказательство:** один `scanner = accounts[0]` читает все цели; при недоступности чата
  следующая учётная запись не пробуется. `_pick_reactor()` выбирает аккаунт чистым hash по
  всему pool и не учитывает `TargetAccountState`/членство/блокировку именно в этом чате.
- **Эффект:** правило может стабильно показывать scan error либо случайно пропускать реакции,
  хотя другой выбранный аккаунт имеет доступ и способен выполнить действие.
- **Что сделать:** строить eligible pool на каждую цель из свежего preflight/target state,
  последовательно пробовать scanner-ов, а reaction task либо назначать доступному аккаунту,
  либо делать контролируемый failover до внешнего действия.

#### RA1-07 — P2: legacy API сохраняет незапускаемый диалог

- **Где:** `src/proxima_traffic/schemas.py:137–262, 302–347` и
  `src/proxima_traffic/api.py:758–767, 889–912, 1223–1310`.
- **Доказательство:** `dialogue_steps` проходит `validate_dialogue_steps()` и Spintax;
  legacy поля `primary_text/reply_text` проверяются только на длину/blank. Payload с
  `primary_text='{broken'` принят `CampaignCreate`. Bot repository тот же текст отклоняет,
  а очередь обнаружит ошибку только через `parse_dialogue_steps()` при запуске.
- **Эффект:** API возвращает успешное создание/изменение кампании, которую затем нельзя
  поставить в очередь; bot и API имеют разные контракты.
- **Что сделать:** применять `validate_spintax()` к обоим legacy полям в create/update или
  нормализовать любой dialogue в единый `dialogue_steps` контракт до записи.

#### RA1-08 — P2: global stop может скрыть уже выполненное внешнее действие

- **Где:** `src/proxima_traffic/services.py:4149–4250` и финализация в
  `reactions.py`, `participant_reactions.py`, `channel_comments.py`.
- **Доказательство:** для CampaignRun в работе ставится `cancel_requested`, а running
  ReactionTask/ChannelCommentRun/ParticipantReactionTask сразу переводятся в `CANCELLED` и
  лишаются lease. Telegram RPC нельзя гарантированно прервать; если он завершится после
  update, worker уже не сможет записать success. В комментариях этот случай прямо
  поглощается как потеря durable ownership.
- **Эффект:** UI говорит «отменено», хотя реакция/комментарий уже появился; pacing/counters
  и отчёт могут не отразить внешнее действие.
- **Что сделать:** secondary-задачам добавить `cancel_requested` и финализировать их после
  возвращения RPC, как CampaignRun; отдельно показывать `cancelled_before_send` и
  `completed_during_cancel`.

#### RA1-09 — P2 качества: фактические скрытые упоминания не видны оператору

- **Где:** audit events `campaign.hidden_mentions_resolved` и
  `channel_comment.hidden_mentions_resolved`; обычные launch/report карточки.
- **Доказательство:** безопасные причины пропуска (нет доступа к participant list, меньше
  пяти подходящих людей, недостаточно места, contact content) остаются только в audit log.
- **Эффект:** переключатель показывает «включено», но оператор не знает, сколько публикаций
  действительно содержало 5–10 упоминаний и почему часть прошла без них.
- **Что сделать:** хранить/агрегировать `requested, resolved_count, skip_reason` по run и
  показывать это в отчёте запуска/правила; это также позволит контролировать качество без
  раскрытия списка участников.

#### RA1-10 — P2 качества: недостаточно настоящих UI/Telegram проверок

- **Где:** весь путь `bot/handlers.py → repository/services → live_gateway.py`.
- **Доказательство:** низкое покрытие handlers/live gateway и только три opt-in Test DC
  теста. Нет реальных Test DC сценариев для reaction, participant scan, discussion comment,
  album/contact, `tg://user` hidden mentions и полного multi-step dialogue.
- **Эффект:** fake gateway хорошо проверяет orchestration, но не доказывает корректность
  каждой кнопки и каждого MTProto-вызова. Поэтому первая половина проверена подробно по
  коду, но не может быть объявлена полностью production-подтверждённой.
- **Что сделать:** добавить критические bot E2E с fake dispatcher и отдельный безопасный
  Test DC smoke-набор на выделенных аккаунтах/чатах.

#### RA1-11 и RA1-12 — P3: качество тестов и установленного окружения

- Два recovery-теста создают fake Telegram message без `out=True`, тогда как production
  фильтр намеренно принимает только исходящие сообщения, чтобы не спутать их с одинаковым

- После исправлений обязательный критерий: полный `pytest`, `ruff`, `compileall`, `pip check`,
  migration doctor и выделенный live smoke должны быть зелёными одновременно.

### Актуальные находки второй половины

#### RA2-01 — P1: @SpamBot может ошибочно освободить ограниченный аккаунт

- **Статус:** **исправлено 06.08.2026**. Общий `good news` удалён из free-маркеров;
  explicit date/permanent restriction проверяются раньше free. Конфликтный ответ теперь
  возвращает temporary restriction и точный UTC expiry.

- **Где:** `src/proxima_traffic/spambot.py:56–81, 410–461` и
  `src/proxima_traffic/spambot_checks.py:190–199`.
- **Доказательство:** `_FREE_MARKERS` содержит слишком общий фрагмент `good news`, а
  `parse_spambot_response()` проверяет free до срока и permanent/restriction markers.
  Воспроизведение с текстом `Good news: your account is restricted until 15 August 2026
  14:30 UTC.` возвращает `free`, `restricted_until=None`. При `FREE` сервис имеет право
  вернуть автоматически поставленный на паузу аккаунт в `ACTIVE`.
- **Эффект:** ограниченный аккаунт может снова попасть в отправки, получить дополнительные
  ошибки/жалобы и усилить Telegram-ограничение. Ошибка относится к безопасности аккаунтов,
  а не только к отображению статуса.
- **Что сделать:** сначала распознавать explicit restriction/permanent и дату; free принимать
  только по полным устойчивым формулировкам и при отсутствии любого restriction marker.
  Противоречивый текст классифицировать как `UNKNOWN`, не активировать аккаунт. Добавить
  таблицу конфликтных локализованных ответов и тест приоритета для каждого языка.

#### RA2-02 — P1: readiness объявляет готовой БД с неприменённой миграцией

- **Статус:** **исправлено 06.08.2026**. `/ready` использует `Database.ready()` и проверяет
  достижимость, единственный Alembic head, обязательные таблицы и колонки. На revision
  `0046` при head `0047` регрессионный тест получает 503; личная БД после миграции даёт 200.

- **Где:** `src/proxima_traffic/main.py:246–274`; полноценная проверка уже существует в
  doctor/operations, но endpoint её не использует.
- **Доказательство:** `/ready` вызывает лишь `database.ping()` и смотрит на worker tasks.
  Текущая БД находится на `0045_notification_delivery_leases`, код ожидает `0046`, doctor
  возвращает unhealthy, однако фактический `/ready` отвечает HTTP 200 и `ready`.
  На отдельной БД миграция 0045→0046 проходит, поэтому это не ошибка миграционного файла.
- **Эффект:** orchestrator/systemd может направить запросы или включить worker с кодом,
  несовместимым со схемой. Ошибка проявится уже внутри очереди запросом к отсутствующим
  lease-колонкам вместо раннего отказа запуска.
- **Что сделать:** при startup и `/ready` сравнивать текущий Alembic revision с единственным
  code head и, при необходимости, проверять обязательные колонки; при несовпадении отвечать
  503 с безопасным кодом причины. `auto_create_schema` не считать заменой миграциям.

#### RA2-03 — P1: изменение прокси не инвалидирует live-клиент другого процесса

- **Статус:** **исправлено 06.08.2026**. ProxyService повышает durable
  `Account.connection_generation` при изменении маршрута; каждый gateway сравнивает
  generation перед операцией, отключает старый cached client и строит новый маршрут.

- **Где:** `src/proxima_traffic/live_gateway.py:84, 877–944`, локальные вызовы закрытия в
  `bot/handlers.py:2961–3415` и `api.py:317–450, 1146–1164`.
- **Доказательство:** каждый `TelethonGateway` хранит собственный `_clients` в памяти.
  После rotate/replace/toggle/assign/release обработчик вызывает `close_account()` только
  на gateway своего процесса. Если управление идёт через API-процесс, а отправляет
  bot-worker, cached client worker-а не видит это закрытие и остаётся подключённым через
  прежний endpoint/IP. БД-lease сериализует Telegram-операции, но не версионирует route и
  не рассылает инвалидирование.
- **Эффект:** оператор видит новый/отключённый прокси в БД, но часть отправок продолжает
  идти по старому IP до случайного reconnect. Это нарушает обещание безопасного маршрута и
  делает ротацию недостоверной именно в раздельном API+bot deployment.
- **Что сделать:** хранить durable `connection_generation`/route revision для аккаунта и
  сравнивать её перед каждой account operation; при изменении маршрута повышать generation
  под account lease. Альтернатива — надёжный pub/sub invalidation, но проверка версии всё
  равно нужна после пропущенного события. Добавить тест с двумя экземплярами gateway.

#### RA2-04 — P2: API сохраняет шаблон с повреждённым Spintax

- **Где:** `src/proxima_traffic/schemas.py:102–120`, `api.py:691–759`; корректный
  bot-контракт — `bot/repository.py:1606–1685`.
- **Доказательство:** `MessageTemplateCreate/Update` ограничивает только длину, API напрямую
  записывает модель. Изолированный HTTP-вызов с `primary_text='{broken'` получил `201` и
  вернул сохранённый повреждённый текст. Bot repository этот же текст отклоняет через
  `validate_spintax()`.
- **Эффект:** в БД появляется шаблон, который один интерфейс считает валидным, а другой не
  сможет безопасно применить; ошибка отложена от места ввода до сборки кампании/рендера.
- **Что сделать:** вынести общую валидацию пары текстов в schema/domain service и применять
  её к create и каждому изменённому полю update; добавить API-тесты unmatched brace,
  пустого варианта и корректного nested Spintax.

#### RA2-05 — P2: зависший delayed-delivery check не имеет дедлайна и не виден readiness

- **Где:** `src/proxima_traffic/delivery_monitor.py:67–87, 139–226` и
  `worker_supervision.py:47–108`, `main.py:252–267`.
- **Доказательство:** `_check_action()` вызывается без `asyncio.timeout`; параллельный
  heartbeat каждые 30 секунд продлевает 120-секундный lease до завершения RPC. Supervisor
  получает success/error только после возврата всей итерации. Его snapshot хранит
  `last_success_at`, но `/ready` проверяет лишь `state == 'running'` и `task.done()`, без
  допустимого возраста последнего успеха. Существующий `BlockingGateway`-тест доказывает,
  что check может ждать внешнее событие неограниченно; он проверяет fencing, но не timeout.
- **Эффект:** один зависший verify останавливает весь последовательный batch, удерживает
  account operation и бесконечно сохраняет владение ActionLog. Процесс и `/ready` при этом
  могут выглядеть здоровыми.
- **Что сделать:** оборачивать одну проверку в настраиваемый deadline; по timeout прекращать
  heartbeat, освобождать lease и назначать bounded retry. Для каждого worker задать максимум
  возраста `last_success_at` относительно его poll/step timeout и возвращать 503/degraded,
  если freshness нарушена. Добавить тест с никогда не завершающимся gateway.

#### RA2-06 — P2: отсутствие admin-прав ошибочно делает цель глобально недоступной

- **Где:** `src/proxima_traffic/live_gateway.py:2466–2481` и
  `services.py:1640–1789`.
- **Доказательство:** `ChatAdminRequiredError` включён в `target_permanent` и преобразуется
  в `target_unavailable`. Это воспроизводимо прямым вызовом mapper. Но admin-право зависит
  от аккаунта: другой отправитель может быть администратором. Один ActionLog с
  `target_unavailable` немедленно делает quality score цели равным нулю, переводит её в
  BAD и отменяет все queued runs, не пробуя доступный аккаунт.
- **Эффект:** рабочий чат глобально помещается в карантин из-за недостаточных прав одного
  выбранного аккаунта; теряется корректный failover и отменяются чужие очереди цели.
- **Что сделать:** классифицировать `ChatAdminRequiredError` как account×target failure
  (`account_banned_in_chat` либо отдельный `account_missing_admin_rights`) и исключать только
  эту пару. `target_unavailable` оставлять для действительно глобально неверного peer/invite.
  Добавить тест двух аккаунтов: первый без admin, второй с правом публикации.

- **Рекомендация:** заменить вызов на `parse_dialogue_steps()` и добавить интеграционный тест
  callback → repository для выбора каждого допустимого шага.

#### FA1-02 — P1: «Остановить все отправки» оставляет работающими комментарии и реакции участников

- **Где:** `src/proxima_traffic/bot/handlers.py:2626–2644` вызывает только
  `RunQueue.cancel_all()`; реализация в `src/proxima_traffic/services.py:4117–4159` отменяет
  `CampaignRun` и `ReactionTask`, но не `ChannelCommentRun` и не
  `ParticipantReactionTask`.
- **Последствие:** текст подтверждения обещает остановить «все отправки», однако правила
  комментариев продолжат отслеживать посты и писать в discussion, а правила реакций
  участников продолжат создавать и выполнять задачи. Это особенно опасно в аварийной
  остановке.
- **Рекомендация:** вынести атомарную глобальную остановку в отдельный coordinator, которому
  доступны все durable queues. Он должен отменять queued-задачи всех типов и передавать
  running-задачам единый stop/fencing-флаг; добавить тест на все четыре типа очередей.

#### FA1-03 — P1: оба worker-а реакций обходят pacing и дневной лимит аккаунта

- **Где:** успешная ветка `ReactionWorker._process()` в
  `src/proxima_traffic/reactions.py:214–267` и
  `ParticipantReactionService._process()` в
  `src/proxima_traffic/participant_reactions.py:561–607` отправляет реакцию и сразу
  завершает задачу. В отличие от комментариев, вызова
  `CampaignRunner.record_external_account_send()` после успеха нет.
- **Последствие:** worker лишь читает уже существующий `account_resume_at`, но новая реакция
  не обновляет `next_send_at`, `sent_today` и micro-break. При большом потоке задач аккаунт
  может без локального ограничения поставить сотни реакций подряд.
- **Рекомендация:** ввести отдельный лимит реакций либо временно учитывать успешную реакцию
  через общий учёт внешней account-операции. Проверить последовательность из нескольких
  reaction tasks: вторая должна переноситься до разрешённого времени, а дневной лимит —
  блокировать дальнейшие действия.

#### FA1-04 — P1: смена первого аккаунта может разорвать уже начатую цепочку комментариев

- **Где:** `ChannelCommentService.replace_primary_account()` в
  `src/proxima_traffic/channel_comments.py:295–383` отменяет только `QUEUED` runs.
  У активного run после отправки первый шаг фиксируется в `_record_delivery()`
  (`:888–943`), а следующий шаг при новом claim строится из текущего, уже изменённого rule
  в `_load_run_context()` (`:768–787`).
- **Сценарий:** старый первый аккаунт уже отправляет первый комментарий диалоговой цепочки;
  оператор сразу заменяет первый аккаунт; отправка завершается, run ставится обратно в
  `QUEUED`; следующий шаг берётся из новой цепочки. В итоге один discussion thread может
  состоять из сообщений разных версий правила/неожиданного автора.
- **Рекомендация:** добавить generation/version к rule и snapshot шагов в `ChannelCommentRun`
  при постановке в очередь. При смене автора помечать и `RUNNING` run как cancel-requested
  либо разрешать ему завершиться строго по исходному snapshot; добавить race-тест с
  блокирующим gateway.

#### FA1-05 — P2: карточки правил комментариев и реакций читают всю историю задач и делают N+1 запросов

- **Где:** `ChannelCommentService.list_rules()` (`channel_comments.py:183–203`) вызывает
  `_rule_view()` на каждое правило; `_rule_view()` читает все статусы его runs
  (`:1077–1094`). Аналогично `ParticipantReactionService.list_rules()`
  (`participant_reactions.py:149–167`) и `_view()` (`:765–785`).
- **Последствие:** с ростом истории каждая страница бота переносит в память все статусы всех
  прошлых задач выбранных правил. Несколько правил превращают это в N+1 SQL-запросов и могут
  блокировать SQLite именно при открытии панели оператора.
- **Рекомендация:** получать счётчики одним агрегирующим `GROUP BY status, rule_id`, а имена
  баз и число целевых чатов — одной bulk-выборкой. Добавить performance-тест с большим числом
  исторических runs и ограничением количества SQL-запросов.

#### FA1-06 — P2: реакции к постам кампании не имеют операторской наблюдаемости

- **Где:** создание `ReactionTask` в `src/proxima_traffic/services.py`, worker в
  `src/proxima_traffic/reactions.py`, bot-слой в
  `src/proxima_traffic/bot/repository.py` и `src/proxima_traffic/bot/renderers.py`.
- **Доказательство:** реакции создаются и обрабатываются отдельными долговечными
  задачами со статусом и текстом ошибки. В bot-слое есть только настройка правила:
  нет выборки агрегатов `ReactionTask`, последних ошибок или ссылки на такие задачи
  из карточки кампании, запуска и отчёта.
- **Последствие:** рассылка выглядит завершённой, хотя связанные реакции находятся
  в повторных попытках или окончательно не отправились; это видно лишь в БД или логах.
- **Рекомендация:** добавить в карточку запуска/кампании счётчики `pending`,
  `processing`, `sent`, `failed`, `cancelled`, последние ошибки и безопасные
  действия для повтора либо отмены ожидающих задач. Отдельно зафиксировать контракт:
  должна ли отмена одного запуска отменять `ReactionTask` с его `run_id`; сейчас
  `RunQueue.cancel_launch` отменяет только сообщения кампании.

### Оставшийся backlog качества (не блокирует корректность)

- **P3 — масштабирование preflight.** `PreflightService._persist()` делает отдельный поиск
  `TargetAccountState` на каждую пару аккаунт×чат. Для крупных баз нужен batch upsert и
  групповой пересчёт качества, чтобы не получать N+1 SQL-запросов.
- **P3 — переживание перезапуска control-бота.** `MemoryStorage` хранит только черновики
  FSM в памяти. Незавершённый мастер создания потеряется после перезапуска, хотя сохранённые
  кампании и задачи в БД не затрагиваются. Для бесшовной работы нужен Redis/БД storage.
- **P3 — поиск запусков.** `search_launches()` получает подробности каждого из максимум 50
  результатов отдельным `get_launch()`. Для большого журнала стоит заменить это bulk-выборкой
  или показывать облегчённую карточку до открытия конкретного запуска.
