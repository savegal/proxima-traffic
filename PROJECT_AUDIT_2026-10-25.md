# Полная проверка Proxima Traffic — 25 октября 2026

Базовая версия: `7f5d7ad`. Проверены текущие исходники, автоматические сценарии, собираемый wheel и рабочая SQLite-база. В рабочей базе выполнялись только чтения. Бот и реальные операции Telegram не запускались.

## Подтверждённые ошибки и исправления

| ID | Ошибка и воспроизведение | Исправление |
|---|---|---|
| P1-01 | Установленный пакет не мог создать базу: в wheel отсутствовали все миграции, а код искал `alembic.ini` возле исходного репозитория. Отдельный процесс вне проекта завершался `Path doesn't exist: .../migrations`. | В wheel включены конфигурация Alembic, 81 миграция и проверяемый файл начального стоп-листа. Общий `migration_config` выбирает ресурсы исходников или установленного пакета. Этот путь используют запуск, диагностика и создание чистой базы. |
| P1-02 | Восстановление приглашений читало истёкшее задание без предварительной блокировки. В тесте heartbeat успевал сохранить новый срок, после чего восстановление перезаписывало задание как FAILED. | Writer lock берётся до чтения истёкших заданий. Проверено реальное соперничество двух SQLite-сессий: выигрывает либо продление, либо восстановление; состояние победителя не затирается. |
| P1-03 | Восстановление больших отменённых запусков ЛС и приглашений использовало неограниченный `NOT IN`. Оба пути падали на 1005 заданиях при реально установленном лимите SQLite 999 параметров. | Терминальные изменения явно сбрасываются в транзакцию до общего UPDATE. Завершённые строки исключаются условием статуса; список всех ID больше не передаётся. Резервации освобождаются, исходы неизвестной доставки сохраняются. |
| P1-04 | Работник историй мог отправлять по старому claim после смены токена. Повторная проверка оператора выполнялась до длительного получения профилей и загрузки медиа, а не у самой отправки. | Проверяются статус задания, токен, срок, назначенный аккаунт, состояние кампании/аккаунта, актуальность сессии и стоп-лист непосредственно перед SendStory/Increment/Read/Reaction. Проверены обе очереди и изменения во время подготовки: пауза, отключение аккаунта, исключение получателя, потеря токена. |
| P1-05 | Потерянный ответ на IncrementStoryViews распознавался как обычная повторяемая сетевая ошибка. Потеря account lease также возвращала задачи публикации/просмотра в очередь, хотя Telegram мог уже выполнить действие. | Такие неоднозначные исходы сохраняются как `delivery_unconfirmed` с запретом автоматического повтора. Точный FloodWait остаётся отдельным подтверждённым отказом; уже подтверждённые просмотры при ошибке следующего действия сохраняются. |
| P1-06 | Одновременное первое открытие общей базы подписчиков давало конфликт уникального имени. При активном импорте новая строка могла возвращаться из функции без commit и исчезать. | Создание через атомарный INSERT ON CONFLICT. Факт создания участвует в решении о commit даже при активном импорте. Проверены восемь одновременных запросов в обоих режимах и наличие единственной сохранённой строки. |
| P2-01 | Исключение в cleanup worker после принудительной отмены выходило из `_finish_background_task` и прерывало завершение остальных ресурсов. Повторяется в боте и API. | Ошибка фиксируется в журнале, завершение продолжается. Отмена самого ожидающего процесса корректно передаётся вызывающему коду после завершения дочернего worker. |
| P2-02 | Ошибка `gateway.close()` в API не позволяла дойти до `database.dispose()`. | Закрытие базы вынесено в finally. Проверено реальным lifespan приложения с неисправным закрытием gateway. |
| P2-03 | Не-ASCII байт в неправильном заголовке администратора приводил к TypeError в `compare_digest` вместо HTTP 401. | Сравниваются исходные байты заголовка и UTF-8 байты настройки. Проверены отказ неправильному заголовку и корректный UTF-8 секрет. |
| P2-04 | `/api/v1/worker` считал зависший worker исправным, пока его task не завершён, хотя freshness уже истекла. | Показатель учитывает запуск основного worker и свежесть отчётов каждого supervised worker. Контрольный тест использует действительно живую, но зависшую задачу. |

Дополнительно приведена к чистому Ruff проверка всего `src`: удалён неиспользуемый импорт, объявления Query переведены на Annotated с сохранением HTTP-алиасов, импорты роутеров перенесены наверх без изменения порядка регистрации, исправлено форматирование длинных строк и сохранён исходный exception cause проверки историй. Косметические изменения не считаются отдельными runtime-дефектами.

- Добавлено 27 проверок: 11 в `test_project_audit.py`, 3 в `test_queue_recovery_audit.py`, 13 дополнительных вариантов в `test_story_quality.py`.
- **Ruff всего `src` проходит**, новые/изменённые тестовые файлы также проходят Ruff. `compileall`, `pip check`, `git diff --check` — без ошибок.
- Финальный wheel установлен через `pip install --no-deps --target` во временный каталог. Отдельный процесс загрузил именно установленный код, создал схему, проверил readiness и выполнил console entry points `proxima-doctor`, `proxima-backup`, `proxima-clean-db`; чистая база прошла doctor.

## Границы результата

Проверка не доказывает реальную доставку Telegram и не воспроизводит внешние ограничения/сбои Telegram живыми аккаунтами. Test DC сценарии остаются opt-in. Рабочие ключи и формат шифрования не менялись. История, очереди, диагностики и пользовательские выгрузки сохранены.
